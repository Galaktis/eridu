# AGENTS.md

Context for coding agents working on **Eridu**. Read this first, then the code.

## The project

Eridu — *"The Epic of your Repository"* — is a Git history visualizer, a 3D take on
[Gource](https://github.com/acaudwell/Gource), written in Rust with Bevy. Git is the only VCS
it will support.

The name is Eridu, the oldest city of Sumer in legend, Uruk's neighbour (Uruk was Gilgamesh's
city). Keep that flavor in naming and ideas: releases are named after the 12
tablets of the Epic ("Tablet I" … 1.0 = "Tablet XII").

- Repo: https://github.com/Galaktis/eridu (MIT, by Galaktis).
- Keep answers short and concrete.
- If an `AGENTS.local.md` exists next to this file (git-ignored), read it too: it holds
  machine-specific notes (local paths, private test repositories).

## Layout

| `src/config.rs` | Command line + `eridu.toml` (auto-loaded from the repo root), `--help` text. |
| `src/git.rs` | Runs `git log --reverse --no-renames --name-status`, parses, filters, resolves `--from/--to`; dates. |

| `src/tree.rs` | Directory tree model + spring layout (3D), file slots, event log for the view. |
| `src/files.rs`, `src/files.wesl` | Draws all files in one instanced draw call (custom render pipeline). |
| `src/identity.rs` | Who's who: groups emails into people (`People`), names them (first names only). No IO. |
| `src/github.rs` | Logins, profile names and avatars from GitHub in a background thread, cached on disk. |
| `src/perf.rs` | `F3` stats overlay and `--bench` (frame-time percentiles, then quits). |
| `src/hud.rs` | Date, status line, file-type legend (`L`), help overlay (`H`), `Esc`; installs the font. |
| `src/colors.rs` | File type of a name, curated colors per type, hashed fallback (`name_color`). |
| `src/sparks.rs` | Deleted files burst into sparks, drawn as extra file-layer instances. |
| `src/branches.rs` | `--branches` (`B`): side-branch changes float as ghosts above their files until their merge. |
| `src/ziggurat.rs` | `--view ziggurat` (`V`): the history as stacked layers (present at the base), built on first use. |
| `src/record.rs` | `--record`: fixed timestep, offscreen render at the video's size, GPU readback, ffmpeg (or PNGs) on a writer thread. |
| `src/pace.rs` | How busy the screen is (changes and commits per second), and what adapts to it: glow length, beam share, how long authors stay. |
| `src/director.rs` | The cinematic camera: picks wide / burst / author shots when the camera is left alone; calm eased moves. |
| `src/interact.rs` | Picking (ray vs. files), `Hover`, `Focus` (tree / author / file), clicks, tooltip, file history panel, `F`. |
| `src/quality.rs` | Quality tiers (bloom, MSAA, sphere detail, sparks), `Q`, `auto` step-down. |

### How it works

- **Several repositories**: each becomes a top-level folder of the one `Tree` (paths prefixed
  with `git::repo_names`), histories merged by `git::merge` (by time, keeping each repo's order),
  `Commit::repo` says where a commit comes from (for GitHub lookups). `Tree::separate_cities`
  pushes the top-level directories' subtrees apart as wholes (`push_cities`).
- **Loading**: `git::history` runs on a background thread (the window opens at once): reads the
  log, drops filtered paths/authors, trims `--to`, and computes the start index (`--from`,
  `--start`). `receive_history` then groups authors, starts the identity thread, and
  `fast_forward`s the commits before the start (no animation, then `Tree::settle`).
- **Merges**: `git log --name-status` shows nothing for merge commits, so files a merge drops
  would linger forever (a 19k-commit repository ended with 1,901 ghost files, svgs from a
  branch merged without them). `git::load` runs a second `git log --merges -m --diff-filter=D` and adds
  those deletions to the merges. Check: `--bench` prints "N files at the end" = `git ls-files | wc -l`.
- **History**: `History` holds the commits; `playback` advances a clock (`seconds_per_day`,
  auto-skips quiet periods) and queues each reached commit's changes in `History::pending`,
  applied at `CHANGES_PER_SECOND × speed` (never slower than clearing the backlog in
  `SWEEP_SECONDS`). The clock waits while the backlog is long.
- **Time travel**: setting `History::seek = Some(commit)` makes `timeline::apply_seek` (before
  `playback`) flush the queue, restore the latest `Snapshot` (tree + scene) before the target if
  it's closer, replay the rest without animation (`Tree::apply(_, None)` + `Scene::absorb` per
  commit, taking snapshots on the way), then settle only the new directories. Startup is just a
  seek to the start position. Snapshots are only offered at commit boundaries (empty queue).
- **Tree (model)**: knows nothing about entities. Files have a stable `FileId` and a slot in their
  directory (`file_offset(slot)`: Fibonacci ball); deleting swaps the last file into the hole.
  Every change is pushed to `Tree::events` (`Added`, `Deleted`, `Touched`).
  Directories are spring-connected nodes (`FixedUpdate` → `Tree::update`); overlap repulsion uses
  sweep-and-prune on x (near-linear). Directories with no files left (in them or below) are
  `alive == false`: no physics, not drawn, ignored by the camera framing.
- **Scene (view)**: files are **not entities**. `sync_scene` drains the tree's events into
  `Scene::files` (kind, last touch, author); touched files go on `Scene::glowing`, the only ones
  that get a beam (`draw_lines`). `update_files` rebuilds one instance list (position, scale,
  color, emissive) each frame, and `files.rs` draws it as **one instanced draw call** of a
  shared sphere (custom pipeline + `files.wesl`, simple ambient + diffuse + emissive shading
  matching the old `StandardMaterial` look; emissive > 1 blooms). One entity per file cost
  ~0.5 µs/file/frame in Bevy's renderer; this costs next to nothing and scales to 100k files.
- **People**: `identity::People` holds one `Person` per *person*, not per email.
  `group_people` links emails through clues (same email, same name ignoring case/accents/word
  order, name squashed equals an email's local part, same GitHub noreply account id, a `[people]`
  alias), with a union-find, then two one-way links: an email's local part spelling one person's
  initials (`jdoe@` ↔ John Doe, never two names), and a laptop email (`ada@MacBook.local`) to the
  only person with that first name. GitHub logins and profile names found later can merge two
  people at runtime (`People::learn`, `merged_into`, `resolve`).
- **Names**: `identity::name` shows a first name, never a last name (anonymity: videos must be
  shareable without last names): the commit names' first name (multi-word names win, capitals are
  last names, usernames like `jdoe`/`AnnaKb7` are recognized), else the GitHub profile's, else
  the login, else the email, each without the last name. Same first names get an initial
  (`Thomas M.`). `--people` prints the result to check it.
- **Authors**: `Authors` = `People` + one UI `Author` per person, same index. Authors are UI
  overlays (round avatar + name) placed on a **halo**: an ellipse in the
  camera's view plane around the tree, active authors evenly spaced and ordered by the screen
  angle of their recent work (`move_authors`), darting towards it on each commit.
- **Identity thread** (`github.rs`): emails are asked in the order they appear on screen
  from the start position (`lookups`). Accounts first: a GitHub noreply email gives login +
  `avatars.githubusercontent.com/u/<id>`; then the cache; with 20+ emails still unknown,
  `GET /repos/{o}/{r}/commits?per_page=100&page=N` (8 pages at a time, until every email is
  seen) maps `commit.author.email` → `author.login` + `avatar_url`; what's left is asked one
  sha each (`commits?sha=…&per_page=1`). Then 8 workers fetch `GET /users/{login}` (profile
  name) and the avatars, sending each `Identity` as soon as it's known. Bevy from an empty
  cache: 1,699 emails in 70 s (was several minutes, one by one). Token from `GITHUB_TOKEN`,
  `GH_TOKEN`, or `gh auth token`. Answers are cached in `%LOCALAPPDATA%\eridu`
  (`identities.json` + `avatars/`, 30 days, 7 for "not found"; failures aren't cached;
  `LOCALAPPDATA` pointed elsewhere gives an empty cache for tests). `Identities` counts the
  answers (the status line shows `avatars N/M` until done); `apply_identities` applies them,
  and a person with several emails shows the avatar of the email with the most commits.
  `--record` holds the history at its start until every answer is in (then 10 more frames).
- **Camera**: `Orbit` auto-rotates, drag to rotate, wheel to zoom. It frames what `Focus` says:
  the live tree, a file, or a followed author's `Scene::work_area` (their `RECENT_FILES`).
  With `Focus::Tree` and 10 s without camera input (drags, wheel, clicks, camera keys, jumps),
  the `Director` (`--camera cinematic`, the default; `C` toggles) frames its own shots: wide,
  a burst of glowing files, or the busiest author's work (wide ≥ 25 s, close 10–20 s, never
  closer than 0.8 of the tree's radius). Moves ease over ~2.5 s with caps on pan, zoom and tilt
  speed: the aim is calm motion and a big part of the project in view, keep it so.
- **Pace** (`pace.rs`): `playback` reports each frame's applied changes and reached commits;
  `Pace` smooths them into rates and eases three settings: how long a change glows (and its
  beam lasts, 1.5 s calm → 0.4 s busy), the share of changes that get a beam (a stable hash
  pick, aiming at ~60 beams on screen), and how long an author stays on the halo after their
  last change (10 s → 4 s). The halo holds at most `MAX_SHOWN_AUTHORS` (20); when more are
  active, those with the most commits in the whole history keep their place (one-commit
  passers-by only show when there's room), and authors off the halo draw no beams. Bevy
  (12k commits, 1,500 authors) at 0.03 s/day went from a wall of avatars and lines to a
  readable tree. `F3` shows the live values.
- **Avatars** are converted to 8-bit RGBA when they decode as 16-bit grayscale (`rgba`): UI
  materials can't sample integer textures, and wgpu then quits (a Bevy contributor's PNG).
- **Lines** (branches, beams) are 1 px (`LINE_WIDTH`, set on the default gizmo group).
- **Heat**: each change adds 1 to a file's `heat`, which halves every 14 days of *history*
  time (`FileView::heat`); beyond the first change a file swells, at most ×1.5 (`swell`), so it
  always shrinks back. Cold files are reset to 0, so the per-frame cost is only for warm ones.
- **Branches** (`--branches`, `B`): `git::mark_side_branches` walks the whole graph (parents
  from `%P`) once per load: the main line is HEAD's first-parent chain, and each main-line
  merge, oldest first, claims what its other parents reach that nothing claimed before
  (`Commit::merged_by`). `Reading::queue` says what reaching a commit does: by default its
  own changes; in branch mode a side commit's changes become ghosts (`Queued::ghost`, drawn by
  `branches.rs` above their files, tied by a thread) and land on the tree at the merge, which
  drops its ghosts in. Playback and jumps both go through `queue`; toggling sets
  `History::remake`, so the next jump drops the snapshots and replays from the start.
  A 19k-commit repository: 14,708 side commits brought by 3,697 merges, up to ~7k ghosts at once.
- **Ziggurat** (`--view ziggurat`, `V`, `View` resource): `Ziggurat::build` reads the whole
  history once (two passes, ~40 ms for 19k commits): each path gets a spot on a square spiral by
  order of first appearance, and the layer count adapts so that all layers hold about
  `LAYER_BUDGET` (80k) files. Past layers are precomputed (spot, kind) lists pushed straight
  into the file layer; the live base is the tree's own files at their spots (`map_files`, ids
  re-mapped after jumps), so glows, heat and beams still work there. `place` says where a file
  is drawn in either view (beams, an author's work area, focus). Picking, branch lines, ghosts,
  sparks and the director are tree-only. 19k commits: 41 layers, 79.6k files, 24.9k paths.
- **Video** (`--record out.mp4 --fps 60 --size 1920x1080`, `record.rs`): Bevy's
  `TimeUpdateStrategy::ManualDuration(1/fps)` makes every frame advance time by exactly one
  frame, so everything time-based (playback, glows, camera) is frame-exact. The 3D camera
  renders into an `Rgba8UnormSrgb` image (`RenderTarget::Image`, also the default UI camera, so
  the HUD goes into the video); a `Readback` entity gets each frame back (rows padded to 256
  bytes), and a writer thread pipes raw RGBA to `ffmpeg` (libx264 crf 18 for mp4/mov/mkv,
  BT.709-tagged) or saves PNGs. The channel holds 4 frames, so a slow encoder slows rendering
  instead of filling memory. A second camera shows the image in the window. Picking is off,
  the quality is fixed (ultra by default), loop is off; the video holds the end for 3 s, waits
  for the late readbacks, then quits. Anything sized from the view uses the 3D camera's
  viewport, not the window (`move_authors`, the backdrop). 19k commits at 1080p60: ~31 fps with
  x264 `medium`, the bottleneck (~60 fps with a cheap codec).
- **Changes carry a `Touch`** (author, commit, animate). Jumps replay with `animate: false`: views
  still count changes and record the last commit/author, but nothing glows or sparks.

## Build, run, test

CI runs the tests on Linux; releases are built for Linux, Windows and macOS.

```sh
cargo build --release               # first build ~15 min (Bevy); incremental: seconds
cargo run --release -- <repo path>
cargo test --release                # unit tests (identity grouping, globs, dates)
cargo clippy --release --all-targets # keep it warning-free (tests included)
cargo llvm-cov --release --open     # coverage report (`cargo install cargo-llvm-cov`)
cargo fmt                           # rustfmt defaults (`rustfmt.toml` only pins LF); CI checks it
```

Always build/run in **release** (the dev profile is optimized too, but release is what's tested).

### Shipping

- `cargo build --profile dist`: what's released (thin LTO, one codegen unit, stripped; ~10 min
  from scratch, about 70 MB on Windows instead of 86). Day-to-day work stays on `release`.
- Bevy's default features are off (`Cargo.toml` lists what's used): no audio, gamepads, glTF,
  scenes or sprites, so Linux needs no ALSA or udev, only `pkg-config libx11-dev
  libxkbcommon-dev libwayland-dev`. A group of unused render/UI features is kept on purpose:
  without it frames were ~1 ms slower (see the comment there); re-bench before trimming more.
- `.github/workflows/ci.yml`: `cargo fmt --check`, tests with coverage (`cargo llvm-cov`, uploaded
  to Codecov, informational only: see `codecov.yml`) + clippy (`-D warnings`) on Linux, each push
  and PR. `.github/dependabot.yml` opens weekly update PRs (Bevy on its own).
- `.github/workflows/release.yml`: on a `v*` tag, builds Windows x86_64, Linux x86_64 (Ubuntu
  22.04, for an older glibc) and a universal macOS binary (`lipo`), and attaches the archives
  and `SHA256SUMS.txt` to a **draft** release. Run by hand, it only builds the archives.
- `.github/workflows/publish.yml`: publishing that release sends it to crates.io (also read by
  `cargo binstall`, see `[package.metadata.binstall]`), the Homebrew tap and winget, each only
  once its secret is set. Templates in `packaging/`; the whole process is in `RELEASING.md`.
  Windows release builds link the C runtime statically (no VC++ Redistributable needed).

### Performance checks

Performance is a first-class feature (see the rules below). Before and after any change
to a hot path, run the bench on the reference repo and compare:

```sh
target/release/eridu --bench path/to/bevy   # prints p50/p95/p99 frame times
```

`F3` shows the live overlay (fps, frame time, entities, directories, files).

### Visual checks

There is no way to see the window except screenshots (Windows):

```powershell
tools\screenshot.ps1 -Repo path\to\bevy -At 20,50 -Out <scratch dir>
```

It prints the PNG paths (open them to look) plus any WARN/ERROR/panic log lines. It finds the
window by title and is DPI-aware — both were needed to get correct captures.

### Reference repositories

Public ones, read-only (never modify a repository you visualize):

- **Bevy** (~12.5k commits since 2019, ~1,500 people): the reference for performance and busy
  scenes.
- **Ruff** (~18k commits since 2022, ~950 people, 11k files at the end): the biggest tree, and
  a good test of who's who (people sharing emails, `contact@` addresses).

Eridu only reads the history, not the files, so clone them without file contents:

```sh
git clone --filter=blob:none --no-checkout https://github.com/bevyengine/bevy
git clone --filter=blob:none --no-checkout https://github.com/astral-sh/ruff
```

Their bots (`renovate`, `dependabot`, `github-actions`, `*[bot]`) are best left out of videos
with `--exclude-user`.

## Environment gotchas

- **TLS proxies**: behind a corporate proxy, some HTTPS hosts (e.g.
  `avatars.githubusercontent.com`) are re-signed by a private CA. `ureq` is configured with
  `RootCerts::PlatformVerifier` (the OS certificate store); don't switch back to bundled webpki
  roots.
- `github.com/<login>.png` 404s for bots and enterprise (EMU) accounts — use the numeric id
  (`avatars.githubusercontent.com/u/<id>`) or the API's `avatar_url`.
- Bevy is **0.20**. APIs differ from older tutorials: `Bloom` lives in `bevy::post_process::bloom`,
  `FontSize::Px(..)`, `px(..)` for `Val`, `BorderRadius` is a `Node` field, `BorderColor::all`,
  `MessageWriter<AppExit>` + `.write(..)`, `Camera::world_to_viewport` returns a `Result`.
  When unsure, read the sources in `~/.cargo/registry/src/*/bevy_*-0.20.*`.

## Conventions

- Match the existing style: small focused functions, doc comments explaining *why*, named
  constants at the top of `main.rs` for every tunable.
- Few dependencies (currently `bevy`, `ureq`, `serde_json`, `serde` + `toml`, `bytemuck`, `winit`
  — the one Bevy uses, for the window icon — and `winresource` at build time); prefer std.
- Network work must never block rendering (background thread + channel).
- Git: only commit/push when asked.

## Performance rules

Every change follows them. Performance is a top priority: smooth on modest machines, stunning on
strong ones.

- **Per-frame cost follows what changes, not the repo size.** Keep lists of "live" things (glowing
  files, beams, particles, active authors) instead of scanning every file every frame.
- **No allocations in hot systems.** Reuse buffers (`Local<Vec<_>>`, fields on resources).
- **No entity per item for things that come in thousands.** Files are instances of one
  draw call (`files.rs`); particles, explosions and similar effects should reuse that pattern.
  An entity per file cost ~0.5 µs/file/frame in Bevy's renderer.
- **Never block a frame.** Network, git and file IO run on background threads with channels.
- **Quality tiers.** `quality = "auto" | "low" | "high" | "ultra"` scales bloom, MSAA, mesh detail
  and particle counts; new effects must plug into them (`quality.rs`). `auto` steps down when
  frames get slow. Weak machines stay smooth; strong machines get every effect.
- **Measure.** `--bench` plays the whole history as fast as possible and prints frame-time
  p50/p99 and peak entity counts. Run it on a large repository (Bevy) before and after any
  change that touches a hot path.
